# Карта проекта alusan

Обновлять этот файл при структурных изменениях (новые роуты, новые общие компоненты, смена источника данных). Дата последнего обновления: 2026-10-05 (ночь).

## Стек

- **Next.js 16** (App Router, Turbopack), **React 19**, **TypeScript**
- **Tailwind v4** — токены цвета через CSS-переменные в `app/globals.css` (`@theme inline`)
- Шрифты через `next/font/google` (`app/layout.tsx`): **Manrope** — единственный шрифт сайта (и заголовки, и текст, разница только в начертании/размере), **JetBrains Mono** — мелкие моно-лейблы (эйбрау, спецификации)
- **Postgres 16 + Prisma 6** — см. раздел "Бэкенд / БД" ниже. Локально БД поднимается через Docker.
- **pnpm**. `render.yaml` в корне — это **не** прод-деплой, а разовый способ показать превью заказчику. Реальный деплой — свой VPS (reg.ru), домен `alusan.pro`, через Docker — см. `workflows/деплой.md`.
- UI-примитивы из shadcn (`components/ui/`), иконки — `lucide-react`

Главная (`app/page.tsx`), каталог (`app/catalog/page.tsx`) и документы (`app/documents/page.tsx`) — серверные компоненты; интерактивные части (бургер-меню, поиск/фильтр, вкладки) вынесены в клиентские `components/home-header.tsx`, `components/catalog-browser.tsx`, `components/documents-browser.tsx`. **Важно:** `SiteFooter` теперь асинхронный серверный компонент (ходит в БД за настройками) — его нельзя рендерить напрямую внутри `'use client'`-страницы (поймали этот баг на `/documents`, когда она ещё была целиком клиентской). Если где-то понадобится `'use client'`-страница — выносить интерактив в отдельный клиентский компонент, `SiteHeader`/`SiteFooter` звать из серверной обёртки. Та же схема у `/admin`: `app/admin/page.tsx` — тонкий серверный компонент (фетчит данные), вся интерактивность (вкладки, формы, смена статуса заявки) — в `components/admin/admin-shell.tsx` (клиент), данные приходят пропами.

### Шкала заголовков

Начертание/трекинг/интерлиньяж h1/h2/h3 заданы один раз в базовом правиле `app/globals.css` (`@layer base`) — руками на каждой странице их больше не выставляем. Размер — два готовых класса там же:

- `.heading-1` — заголовок страницы (`text-6xl sm:text-7xl`), используют `/catalog`, `/catalog/[category]`, `/contacts`, `/cooperation`, `/documents`, `/technology`
- `.heading-2` — заголовок секции (`text-5xl sm:text-6xl`), используют секции на `/` и `/about`

Главные hero-заголовки (`/` и `/about`) — исключение, у них свой `clamp()`-размер, это осознанно (единственный настоящий "hero" на сайте).

## Бэкенд / БД

Данные каталога и статей больше не хардкод — реальный Postgres через Prisma.

**Поднять локально:**

```
docker compose up -d          # Postgres в контейнере, см. docker-compose.yml
npx prisma migrate dev        # применить схему (prisma/schema.prisma)
pnpm db:seed                  # наполнить категориями/товарами/статьями
pnpm db:studio                # опционально — GUI для БД (Prisma Studio)
```

`.env` — `DATABASE_URL`, не коммитится (см. `.env.example` для формата). Локальный Postgres поднят в докере на порту **5434**, не 5432 — на машине уже висел нативный Windows-сервис Postgres на 5432, конфликтовали.

**Схема (`prisma/schema.prisma`):** `Category`, `Product` (связан с `Category`, `slug` уникальный — для `/catalog/[category]/[product]`; `images String[]` — несколько фото, первое из массива используется как превью на карточках), `Article` (тело — Markdown, статус `draft`/`published`), `Document` (карточки `/documents`: `category` — просто строка-ярлык вкладки, не отдельная таблица, см. комментарий в схеме; `fileUrl` — nullable, кнопка "Скачать" задизейблена пока файла нет), `Lead` (заявки — реально пишутся с сайта, статус `new`/`contacted`/`closed` меняется из админки), `AdminUser` (несколько аккаунтов с ролями, см. "Авторизация и роли админки" ниже), `SiteSettings` (одна строка: `phone`/`email`/`city`/`address`, читают шапка/футер/`/contacts`/главная через `lib/settings.ts`, редактируется из `/admin` → вкладка "Настройки"), `Asset` (файлы — фото товаров и PDF документов, хранятся прямо в БД как `bytea`, см. "Загрузка файлов" ниже).

**Data-access слой:**

- `lib/products.ts` — `getCategories`, `getCategoryBySlug`, `getAllProducts`, `getProductsByCategorySlug`, `getProductsByNames`; для админки отдельно `getAllProductsForAdmin` (то же самое + `categoryId` для формы редактирования — публичный `Product` намеренно сплющивает категорию до строки-названия, админке нужен реальный id)
- `lib/articles.ts` — `getPublishedArticles`, `getPublishedArticleSlugs`, `getArticleBySlug`; для админки `getAllArticlesForAdmin` (включая `draft`, с `id`/`status`/`body` для редактирования)
- `lib/documents.ts` — `getAllDocuments` (вкладки на `/documents` фильтруются на клиенте в `DocumentsBrowser` по уже загруженному списку, отдельного запроса на вкладку нет), `DOCUMENT_CATEGORIES` — фиксированный список вкладок (`Сертификаты`/`Паспорта`/`Документация`), используется и на публичной странице, и в форме создания документа в админке
- `lib/settings.ts` — `getSiteSettings` (с фолбэком на захардкоженные значения, если строки в БД ещё нет), `telHref` (нормализует телефон в `tel:` — учит на баге, который уже ловили: на главной `tel:`-ссылка когда-то не совпадала с тем, что показывалось)
- `lib/leads.ts` — `getAllLeads` (сортировка по дате, новые сверху)
- `lib/admins.ts` — `getAllAdmins` (без `passwordHash`, только для вкладки "Пользователи")

**Server actions (`lib/actions/`):** мутации идут не через API-роуты, а через Next.js server actions (файлы с `'use server'`), это единственный способ писать в БД с фронта в этом проекте. Везде в CRUD-actions (`categories.ts`, `products.ts`, `articles.ts`, `documents.ts`) — проверка `getCurrentAdmin()` в начале (любая роль, не только owner — каталог/статьи/документы доступны и менеджеру), бросает `Unauthorized`, если сессии нет.

- `leads.ts` — `submitLead(source, prevState, formData)` (вызывается через `.bind(null, 'homepage' | 'contacts')` из `<LeadForm action={...}>`, возвращает `{ok, error}` для `useActionState`), `updateLeadStatus(leadId, status)` (дёргается напрямую из `admin-shell.tsx` через `useTransition`, не форма)
- `settings.ts` — `updateSiteSettings(prevState, formData)`, вызывает `revalidatePath('/', 'layout')`, чтобы шапка/футер/контакты везде обновились сразу
- `auth.ts` — `login(prevState, formData)` (ищет `AdminUser` по email **или** телефону — поле `identifier` в форме, проверяет пароль, ставит cookie-сессию, редиректит на `/admin`), `logout()` (чистит cookie), `changePassword(prevState, formData)` (текущий пароль + новый, ≥8 символов)
- `profile.ts` — `updateProfile(prevState, formData)` — каждый редактирует только свой профиль (имя/фамилия/email/телефон), берёт `adminId` из сессии, а не из формы
- `admins.ts` — `createManager(prevState, formData)` и `deleteManager(adminId)` — **только для `role: 'owner'`**, проверка роли внутри самого action через `getCurrentAdmin()`, а не только скрытая кнопка в интерфейсе (важно: `proxy.ts` проверяет лишь "залогинен ли", не роль — см. предупреждение в доках Next про Server Functions ниже)
- `categories.ts` / `products.ts` — CRUD каталога. `deleteCategory` отказывает, если в категории ещё есть товары (считает `db.product.count`, не каскадит удаление молча). Все мутации триггерят `revalidatePath` на `/admin`, `/catalog` и конкретную `/catalog/[slug]` (и старую, и новую, если товар переехал в другую категорию).
- `articles.ts` — CRUD статей. При первом переключении статуса в `published` простав `publishedAt = new Date()`, если его ещё не было — повторная публикация после черновика не сбивает исходную дату.
- `documents.ts` — CRUD документов, `category`/`color` — select из фиксированных пресетов, не свободный текст (см. ниже про Tailwind).

**Важный нюанс по `Product.tone` и `Document.color`:** это строки с Tailwind-классами (`from-[#..] via-[#..] to-[#..]` / `bg-[#..]`), применяются напрямую как `className`. Tailwind v4 генерирует CSS только для классов, которые видит в файлах проекта при сборке — значение, сохранённое только в БД (а не где-то в коде), не даст стиля. Поэтому в формах `ProductForm`/`DocumentForm` это `<select>` с пресетами (`lib/product-tones.ts` / `lib/document-colors.ts`), а не текстовое поле — иначе админ мог бы вписать новый цвет, который молча не применится.

**Авторизация и роли админки:** своя, без Auth.js — так и планировали (см. `план-доработки.md`). Пароль хешируется `bcryptjs` (`lib/password.ts`), сессия — JWT в httpOnly-cookie `admin_session`, подписывается/проверяется через `jose` (`lib/auth.ts`, секрет — `AUTH_SECRET` в `.env`, **меняется — все сессии разом инвалидируются**). `proxy.ts` в корне проекта (см. ниже про переименование из `middleware.ts`) проверяет куку на всех `/admin/*`, кроме `/admin/login`, и редиректит на логин, если сессии нет.

**Скользящая сессия:** `SESSION_MAX_AGE` в `lib/auth.ts` — не "сессия живёт N часов с момента логина", а "можно не заходить N часов, потом разлогинит" (`ADMIN_SESSION_IDLE_HOURS` в `.env`, по умолчанию 5). Каждый заход на `/admin/*` в `proxy.ts` выписывает новый токен с продлённым сроком и перезаписывает cookie (`sessionCookieOptions()` — общая функция для cookie-опций, используется и тут, и в `login`). Так активный пользователь никогда не словит разлогин посреди работы, а забытая/угнанная сессия всё равно гаснет сама.

Вход — по email **или** телефону (`lib/phone.ts` нормализует номер при сравнении). Два уровня доступа (`AdminRole`): `owner` — полный доступ + вкладка "Пользователи" (создание/удаление менеджеров), `manager` — всё остальное без неё. Это разделение прав проверяется **в самом server action** (`admins.ts`), а не только скрытием вкладки в интерфейсе — official Next.js docs прямо предупреждают, что proxy/middleware не защищает Server Functions сама по себе, если изменится matcher или роут, поэтому авторизация всегда должна быть внутри самого action.

Первый админ (`role: 'owner'`) создаётся сидом (`ADMIN_EMAIL`/`ADMIN_PASSWORD` из `.env`, создаётся один раз, повторный `pnpm db:seed` пароль не перезатирает — дальше пароль меняется через вкладку "Профиль", не напрямую в БД).

**`middleware.ts` → `proxy.ts`:** в Next.js 16 файл `middleware.ts` переименован в `proxy.ts` (функция `middleware` → `proxy`), старое название помечено deprecated и выводит предупреждение в dev-режиме. Увидели это на практике при добавлении защиты `/admin` — сразу завели файл с новым именем, конвенция описана в `node_modules/next/dist/docs/01-app/03-api-reference/03-file-conventions/proxy.md` (см. правило в `AGENTS.md` — читать локальные доки перед тем, как полагаться на память о Next.js API, они тут реально разъезжаются с привычным).

**Сидинг (`prisma/seed.ts`):** данные каталога — из `prisma/seed-data.ts` (перенесены из бывшего `lib/data/products.ts`, файл удалён). Статьи — из `prisma/seed-articles.ts`, это текст из `наполнение ai.docx` **как есть**, но с уже убранными названиями моделей конкурента (`BT Pro`, `HH1` — см. план, пункт про alumet.ru). Финальный редакторский проход (тон, бренд-нейминг после решения) ещё предстоит — статьи уже `published`, чтобы видеть рабочий раздел, а не заглушку. Документы — из `prisma/seed-documents.ts`, те же 7 карточек, что были раньше захардкожены в `documents-browser.tsx`, `fileUrl` у всех пока `null`.

**Загрузка файлов:** фото товара (`images`, можно выбрать сразу несколько) и файл документа (`file`) в формах `/admin` — реальные file-инпуты, не ссылки. `lib/assets.ts` → `saveAsset(file, maxBytes)` сохраняет файл в таблицу `Asset` (`bytea`), возвращает URL вида `/api/assets/<id>`, который и попадает в `Product.images`/`Document.fileUrl` — остальной код (`ProductCard`, `DocumentsBrowser`) ничего не знает про источник, просто рендерит `<img src>`/ссылку как раньше. Лимиты — 5 МБ на фото, 15 МБ на документ (`MAX_IMAGE_BYTES`/`MAX_DOCUMENT_BYTES`). **Важная связанная правка:** у Server Actions в Next.js по умолчанию лимит тела запроса 1 МБ — увеличил до 20 МБ через `experimental.serverActions.bodySizeLimit` в `next.config.mjs`, иначе загрузка файла размером больше ~1 МБ падала бы с ошибкой.

**Несколько фото на товар.** `createProduct`/`updateProduct` ДОБАВЛЯЮТ новые файлы к уже загруженным (`images: [...existing, ...new]`), не заменяют — убрать конкретное фото можно только через отдельный `removeProductImage(productId, imageUrl)` (кнопка × на миниатюре в админке), который вдобавок удаляет сам `Asset`, а не только ссылку из массива (в отличие от удаления всего товара/документа, где осиротевший `Asset` осознанно не чистится — см. известные ограничения).

**Клик по товару.** `ProductCard` раньше ничего не делал по клику (стрелка в углу была чисто декоративной — наследие v0). Теперь клик открывает `ProductQuickView` (модалка, портал в `document.body` — важно из-за `overflow-hidden` на `teaser`-варианте карточки, обычный dropdown/absolute внутри неё был бы обрезан), оттуда — переход на полноценную страницу товара `/catalog/[category]/[product]`.

**Документы: открыть vs скачать.** Раньше у карточки документа была декоративная "лупа" (ничего не делала) и единственная кнопка со `download`-атрибутом (всегда форсила сохранение на диск, открыть во вкладке было нельзя). Теперь превью-макет документа — это `<a target="_blank">` без `download`, ведёт на `/api/assets/<id>` напрямую: роут не выставляет `Content-Disposition`, так что PDF/картинка открывается инлайн в браузере. Кнопка со скрепкой со значком "скачать" (с атрибутом `download`) осталась рядом как отдельное явное действие "сохранить на диск".

**Важно:** товары по-прежнему отображаются абстрактной "лестницей"-градиентом (`ProductCard`, поле `tone`), реальных фото товаров и файлов документов в проекте пока нет (поля пустые) — но механизм их загрузки уже готов, заказчику достаточно зайти в `/admin` и прикрепить файлы напрямую.

## Деплой

Подробная пошаговая инструкция — `workflows/деплой.md`. Коротко про файлы и решения:

- `Dockerfile` — многоступенчатая сборка (`deps` → `builder` → `runner`), финальный образ — Next.js `output: 'standalone'` (next.config.mjs), минимальный рантайм без лишних `node_modules`. Базовый образ — `node:22-slim` (Debian, не alpine — у Prisma исторически больше проблем с musl/alpine).
- `docker-compose.prod.yml` — `db` (Postgres) + `migrate` (одноразовый, `prisma migrate deploy && pnpm db:seed`, `app` стартует только после его успешного завершения через `condition: service_completed_successfully`) + `app` + `caddy` (авто-HTTPS через Let's Encrypt, конфиг — `Caddyfile`, 3 строки). Том `alusan_prod_db` **намеренно** назван не так, как в локальном `docker-compose.yml` (`alusan_db`) — у обоих файлов один и тот же дефолтный project name (имя папки), одинаковое имя тома/контейнера привело бы к тому, что прод-compose случайно подцепил бы/подменил локальный dev-контейнер (поймали это на практике при локальном тесте, см. ниже).
- **`migrate` всегда гоняет и миграции, и сид**, не только при первом деплое — `prisma/seed.ts` идемпотентный (upsert для каталога/статей/документов, create-once для админа/настроек), так что это безопасно. Важно почему: без этого между стартом `app` и ручным сидом есть окно, в которое первый заход на ещё не существующую страницу товара/категории закэширует 404 у Next, и он не пропадёт сам даже после того, как данные появятся (это реальный баг, который поймали и воспроизвели при локальном Docker-тесте — см. следующий пункт).
- **`force-dynamic` на DB-страницах.** `/`, `/catalog`, `/articles`, `/contacts`, `/documents`, `/about`, `/cooperation`, `/technology` — везде стоит `export const dynamic = 'force-dynamic'`. Причина: без него Next пытается статически отрендерить эти страницы **во время `next build`**, что требует живой БД в момент сборки — при сборке Docker-образа БД ещё не поднята, сборка падала с `Can't reach database server`. `generateStaticParams` у `/catalog/[category]` и `/articles/[slug]` по той же причине теперь возвращают `[]` (раньше ходили в БД за списком слагов) — страницы рендерятся по требованию при первом заходе (`dynamicParams: true`) и дальше кешируются/обновляются через `revalidatePath` в CRUD server actions, как и раньше.
- **`revalidatePath` при создании, не только при редактировании.** `createCategory`/`createArticle` теперь дополнительно ревалидируют конкретный новый путь (`/catalog/<slug>`, `/articles/<slug>`), не только списочную страницу — иначе если кто-то уже заходил по этому URL до создания записи (получил 404), кэш этого конкретного 404 не сбросится при простом `revalidatePath('/catalog')` (revalidatePath по умолчанию чистит только сам переданный путь, не дочерние динамические).
- **`@vercel/analytics` убран** — тянулся из исходного v0-скаффолда, в dev-режиме не рендерился (`NODE_ENV !== 'production'`) и ни разу не всплывал за всю сессию. В первом же тесте прод-сборки показал себя — 404 на `/_vercel/insights/script.js`, потому что компонент реально работает только при хостинге непосредственно на Vercel. На Render и тем более на своём VPS это чистый мёртвый груз, который генерирует лишний проваленный запрос на каждой загрузке страницы — удалили `<Analytics />` из `app/layout.tsx` и зависимость из `package.json`.
- Весь стек (сборка → миграции → сид → логин в админку → отдача всех публичных страниц) прогнан и проверен локально через `docker compose -f docker-compose.prod.yml` с изолированным project name (`-p`), прежде чем писать инструкцию для реального VPS.

## Дизайн-токены (`app/globals.css`)

Под `@theme inline` объявлены `--color-brand-*`, переиспользуются в Tailwind как `bg-brand-ink`, `text-brand-muted` и т.д. Палитра — реальные цвета логотипа: `--brand-blue` (`#044b8a`, основной, используется в тексте/кнопках/акцентах) и `--brand-blue-dark` (`#033a6b`, приглушённый — для больших сплошных плашек-секций, чистый `--brand-blue` на весь экран оказался слишком ярким). `--brand-lime` (`#9bc538`, зелёный) — **только акцент**: мелкие лейблы, иконки, hover, маленькие кнопки, никогда не фон большого блока (на светлом фоне ещё и `--brand-lime-ink`/`--brand-muted` — затемнённые варианты для читаемости мелкого текста). `--brand-surface-1/2/3` — тёмные навy-тона для шапки/hero/футера.

**Сайт только светлый, тёмной темы нет — сознательно.** Изначально в `globals.css` жил унаследованный от v0/shadcn `.dark`-класс + `@media (prefers-color-scheme: dark)` блок — реальный сайт их не использует (только `--brand-*` выше), но `body` наследовал shadcn-токен `--foreground` через `text-foreground`, который эти блоки незаметно переключали в тёмной системной теме. Результат — текст местами сливался с фоном (особенно в полях форм, см. `план-доработки.md`). Оба блока снесены целиком, `body` переведён на `text-brand-ink`/`bg-brand-paper` напрямую, `colorScheme: 'light'` зафиксирован в `app/layout.tsx` (было `'light dark'`) — сайт больше не меняется от системной темы пользователя, и это не баг, а единственный продуманный вариант дизайна. Если когда-нибудь понадобится тёмная тема — это отдельная, настоящая дизайн-задача, а не включение рубильника.

## Известные ограничения (что не работает по-настоящему)

- `/admin` — CRUD готов везде (каталог, статьи, документы, заявки, настройки, пользователи), включая загрузку файлов. Чего нет: редактирования статичных страниц (`/about`, `/cooperation`, тексты главной) — см. `план-доработки.md`, это осознанно не в скоупе
- Удаление товара/документа не чистит привязанный `Asset` — файл остаётся в БД "осиротевшим". Несрочно (см. `план-доработки.md`), но известный долг
- Нет реальных фото товаров (на hero и в секции "Сделано в России" теперь реальные фото — `hero-ladders.jpg`, `production-assembly.jpg`, но на карточках товаров всё ещё абстрактная градиентная "капсула") — заказчик пришлёт позже, механизм загрузки уже готов
- Статьи опубликованы с текстом из наполнения без финального редакторского прохода (см. раздел "Бэкенд / БД")
- Восстановление пароля "забыл пароль" (по почте/смс) не сделано — только смена пароля из вкладки "Профиль", когда уже залогинен
